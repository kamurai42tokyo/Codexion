mutex を図で理解する

Codexion 用メモ ･ ドングルの取り合いを例にする
この資料の流れ
  1. データの置き場所：ドングルの実物は1か所だけにある
  2. 鍵なしの事故：2人が同じドングルを取ってしまう
  3. 鍵ありの流れ：①確認と②更新の間に誰も入れない
  4. mutex は順番を決めない
  5. 待ち行列との分担：順番は fifo / edf が決める

1データの置き場所

ドングルの実物（t_dongle）は、dongles という配列の中に1本ずつ置かれる。各 corder は、ドングルの実物ではなく、実物の住所（ポインタ）を left と right に持つ。

コーダーかドングルをクリックすると、その対象につながる矢印が強調される。

ドングルをクリックすると、そのドングルを指している corder が分かる。
隣どうしの corder 2人は、同じ1本のドングルの住所を持つ。住所の先にある実物は1つなので、片方の corder が書き換えた状態は、もう片方の corder にもそのまま見える。

2鍵なしの事故

corder A と corder B は、同じドングルを次のコードで取ろうとする。このコードは mutex を使っていない。

if (dongle->in_use == false)   // ① check
	dongle->in_use = true;     // ② update

「次へ」を押すと、時刻が1つずつ進む。横軸は時刻を表し、縦の段は各 corder が実行している処理を表す。

①確認②更新事故
事故の原因は、corder A の①確認と②更新の間に、corder B の①確認が入り込んだことにある。corder A が①で得た「空いている」という結果は、②の時点ではもう正しくない。

3鍵ありの流れ

次のコードは、①確認と②更新を lock と unlock の間に入れている。lock から unlock までの区間は クリティカルセクション（割り込まれてはいけない区間）と呼ばれる。

pthread_mutex_lock(&dongle->mutex);   // take the key (wait if someone has it)
if (dongle->in_use == false)          // ① check
	dongle->in_use = true;            // ② update
pthread_mutex_unlock(&dongle->mutex); // give the key back
lock / unlock①確認②更新lock の行で待機
CPU の上では、①と②は別々の命令として順に実行される。それでも corder B は、corder A の①と②の間の状態を一度も見られない。そのため、corder B から見ると、corder A の①と②は割り込めない1つの処理として振る舞う。

mutex が待たせる相手は、同じ mutex を lock しようとしたスレッドだけである。in_use を鍵なしで触る行が1か所でもあれば、その行ではこの防御が働かない。

4mutex は順番を決めない

鍵が返されたとき、次にどの corder が鍵を取るかは、OS のスケジューラ（どのスレッドをいつ動かすかを決める OS の仕組み）が決める。mutex は、待ち始めた順番を覚えていない。

「unlock する」を押すと、今の持ち主が鍵を返し、待っている corder の中から次の持ち主が選ばれる。鍵を返した corder も、すぐにまた lock を呼んで取り合いに加わる。

鍵（mutex）を今持っている corder

lock の行で待っている corder（並び順に意味はない）

    赤い行は、「一番長く待っている corder」以外の corder が鍵を取った回を表す。

    この図は、「順番が保証されない」ことを表すために、次の持ち主をランダムに選んでいる。実際の OS は、サイコロではなく OS 内部の都合で次のスレッドを選ぶ。どちらの場合でも、プログラムは選ばれる順番をあてにできない。

    鍵を何度も取り逃がして待ち続ける状態は、starvation（飢餓）と呼ばれる。mutex だけでは starvation を防げない。

    5待ち行列との分担

    課題文は、ドングルを fifo（要求が届いた順）か edf（燃え尽き期限が一番早い順）で渡すことを求めている。この順番は、各ドングルが持つ待ち行列（自作のヒープ＝優先度付きの並び）が決める。mutex は、待ち行列を操作している最中に割り込まれないように守る。
