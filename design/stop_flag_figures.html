この資料の例では、run_simulations が corder を3人作ろうとする。corder 1 と corder 2 のスレッドは作成に成功し、corder 3 のスレッドは作成に失敗する。run_simulations は、失敗に気づいたあと、作成済みの corder 1 と corder 2 を pthread_join で待つ。

1stop も stop_mutex もない場合

corder のスレッドは、次のような終わらないループを回る。このループには、外から止める条件がない。

while (1)
{
	// take dongles, compile, debug, refactor ...
}

「次へ」を押すと、時刻が1つずつ進む。横軸は時刻を表し、縦の段は各スレッドが実行している処理を表す。

通常の処理join で待機失敗・問題
pthread_join は、相手のスレッドが関数から return するまで待ち続ける。相手のスレッドがループを抜ける手段を持たなければ、join も終わらない。

2stop だけある場合

corder のループ条件が stop を見るようになる。main スレッドは、失敗に気づいたら stop に true を書く。しかし、どちらの読み書きも鍵（mutex）を使っていない。

// corder thread
while (corder->data->stop == false)
{
	...
}

// main thread (on failure)
data.stop = true;
stop を読むstop に書くjoin で待機失敗・問題終了
「stop だけ」の版は、試しに動かすと正しく止まることも多い。しかし、正しく止まる保証はない。保証のないプログラムは、評価のときや別の環境で突然固まることがある。

データ競合は、cc -fsanitize=thread でビルドするか、valgrind --tool=helgrind で実行すると検出できる。42 の評価でも、この2つのツールでデータ競合を確認されることが多い。

3stop と stop_mutex の両方がある場合

stop を読み書きするスレッドは、必ず先に stop_mutex を lock する。読み書きが終わったら、そのスレッドは stop_mutex を unlock する。この決まりを守らせるために、読み書きを set_stop と is_stopped の2つの関数に閉じ込める。

// corder thread
while (is_stopped(corder->data) == false)
{
	...
}

// main thread (on failure)
set_stop(&data);
lock / unlockstop を読む・通常の処理stop に書く待機失敗終了
mutex の lock と unlock は、「ここまでに書いた値を、次に鍵を取ったスレッドに必ず見せる」ことも保証する。そのため、main スレッドが unlock したあとに鍵を取った corder は、必ず true を読む。

void	set_stop(t_data *data)
{
	pthread_mutex_lock(&data->stop_mutex);
	data->stop = true;
	pthread_mutex_unlock(&data->stop_mutex);
}

bool	is_stopped(t_data *data)
{
	bool	stop;

	pthread_mutex_lock(&data->stop_mutex);
	stop = data->stop;
	pthread_mutex_unlock(&data->stop_mutex);
	return (stop);
}
