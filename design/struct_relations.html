1全体の関係図

実線と点線は、今の codexion.h にすでに書かれている関係を表す。オレンジの破線は、これまでの相談で提案したが、まだ codexion.h に書かれていない関係を表す。

構造体の箱をクリックすると、その構造体につながる線が強調され、下に説明が出る。

埋め込み（中に丸ごと入っている） ポインタ（住所を持つ） 番号で対応 予定（未追記）
構造体の箱をクリックすると、その構造体の説明がここに出る。

2つながり方は3種類ある

埋め込み

中に丸ごと入っている

外側の構造体が、内側の構造体の実物をメンバとして直接持つ。外側を1つ作ると、内側も一緒に1つできる。

t_table.config      // t_config 1個
t_dongle.queue[2]   // t_request 2個
ポインタ

住所を持つ

構造体は、相手の実物ではなく、相手が置かれている場所（アドレス）だけを持つ。何人の corder が同じ住所を持っても、相手の実物は1つのままである。

t_corder.table      // t_table の住所
番号で対応

同じ番号を持つ

t_request は corder の住所を持たず、corder の番号（id）だけを持つ。t_request.id と t_corder.id が同じ値なら、その申込書はその corder が出したものである。

t_request.id == t_corder.id
埋め込みとポインタの違いは、「書き換えが誰に見えるか」に表れる。t_table は1つしかなく、全 corder は同じ t_table の住所を持つ。そのため、main スレッドが t_table.stop を書き換えると、全 corder がその書き換えを見られる。

3実体はいくつ作られるか

下の表の N は、引数で受け取った corder の人数（number_of_coders）を表す。

構造体何の数に応じるか実体の数実体の置き場所
t_table人数に関係ない1個run_simulations が1つだけ用意する。
t_config人数に関係ない1個t_table の中（table.config）に埋め込まれる。
t_cordercorder の人数N 個set_corders が malloc した配列。corder 1人につき1個で、スレッドも1本ずつ対応する。
t_donglecorder の人数（円卓では、ドングルの本数が人数と同じになる）N 個ドングルの配列。corder と同じ人数分だけ作る。予定
t_requestドングルの本数 × 22 × N 個の枠各 t_dongle の中の queue[2]。使われている枠の数は、各ドングルの queue_size が表す。

t_dongle が N 本になる理由

円卓では、隣り合う corder 2人の間にドングルが1本ずつ置かれる。N 人の corder が円に座ると、隣どうしの「間」も N か所できる。そのため、ドングルの本数も N 本になる。

t_request が「枠」である理由

各 t_dongle は、queue[2] として t_request を2個分の枠で持つ。ドングルが N 本あるので、枠は全部で 2 × N 個になる。ただし、枠の中で実際に申込書が入っている数は、各ドングルの queue_size（0〜2）が表す。

今の main.c は、t_config を malloc で別に作っている。t_table ができたら、main.c が作った t_config の中身は、t_table の config にコピーされることになる。

4スレッドから値までの辿り方

各スレッドは、pthread_create の第4引数で受け取った住所1つから、必要な値まで矢印を辿っていく。

辿るスレッド欲しい値辿り方
corder スレッドコンパイルにかかる時間corder->table->config.time_to_compile
corder スレッド止まるべきかis_stopped(corder->table)
関数の中で table->stop_mutex を取ってから table->stop を読む。
corder スレッド左のドングルの鍵 予定corder->left->mutex
monitor スレッドi 番目の corder の最終コンパイル開始時刻 予定table->corders[i].last_compile_start
ドングルを渡す処理次に渡す corder の番号dongle->queue[0].id

ドットとアローの使い分け：左側が構造体の実物なら .（ドット）を使い、左側が構造体の住所（ポインタ）なら ->（アロー）を使う。table->config の結果は t_config の実物なので、その続きは .time_to_compile になる。

5予定の関係を追記するときの注意

予定の関係を全部追記すると、t_table は t_corder の住所を持ち、t_corder も t_table の住所を持つ。2つの構造体が互いを指すので、どちらを先に定義しても、片方の名前がまだ宣言されていない状態になる。

この問題は、構造体の名前だけを先に宣言する「前方宣言」で解決できる。ポインタのメンバを書くだけなら、コンパイラは相手の中身を知らなくてよく、名前さえ知っていればよい。

typedef struct s_corder	t_corder;
typedef struct s_dongle	t_dongle;

typedef struct s_table
{
	t_config		config;
	bool			stop;
	pthread_mutex_t	stop_mutex;
	t_corder		*corders;
	t_dongle		*dongles;
}	t_table;

struct s_corder
{
	...
};

前方宣言で typedef を済ませた構造体は、本体の定義で typedef を繰り返さず、struct s_corder { ... }; の形で書く。
